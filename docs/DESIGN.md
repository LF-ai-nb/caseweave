# 设计说明

CaseWeave 的核心目标是：在可解释、可复现的前提下，用尽量少的用例覆盖配置空间里的关键交互。

## 为什么不是随机测试

随机性质测试很适合发现输入空间里的意外行为，但它的覆盖结果通常依赖种子、样本数量和失败收缩过程。CaseWeave 选择另一条路：把每个参数值组合成明确的覆盖目标，然后生成一份可以验证、可以导出、可以放进测试计划的矩阵。

两者可以并存：随机测试用于探索未知，CaseWeave 用于保证“这些组合交互一定被跑过”。

## 数据流

1. `ScenarioSpec::parse` 可选地把行式场景规格解析成模型、约束、包含样例、排除样例和风险提示。
2. `Model::new` 校验参数和取值。
3. `Constraint::parse` 把约束 DSL 转成 AST。
4. `exclude` 样例被转成 `not (...)` 约束，避免生成现实中不允许的组合。
5. 生成器递归枚举候选行，并在部分赋值阶段提前剪枝。
6. `collect_interactions` 收集所有可行候选中的 t-way 交互。
7. `greedy_cover` 选择每轮覆盖新增交互最多的候选行。
8. `remove_redundant_rows` 从后向前删除不影响完整覆盖的行。
9. `include` 样例被合并回最终计划，保证关键业务路径不会被压缩算法删除。
10. `audit` 用同一套交互集合验证任意用例集。
11. 风险提示为每条用例打分，生成可解释的优先级排序。
12. `ScenarioGate` 把覆盖、风险和 lint 结果汇总成 CI 门禁报告。
13. `plan_repair` 可以对不完整的外部套件生成补测步骤，逐步覆盖缺失交互。
14. `RepairGate` 检查补测计划是否完整、是否超预算，以及剩余缺口是否可接受。

## 确定性

CaseWeave 不使用随机数。参数顺序、取值顺序、候选枚举顺序、贪心 tie-break 和冗余删除顺序都固定，因此相同模型和约束会得到完全相同的输出。

## 约束求值

约束在未完整赋值时使用三值逻辑：

- `Yes`：当前部分赋值已经满足
- `No`：当前部分赋值必然违反
- `Unknown`：还需要等待后续参数取值

只要某个约束返回 `No`，枚举器就停止深入该分支，减少无效候选。

## 复杂度边界

覆盖数组生成的难点在于候选空间会随参数数量指数增长。CaseWeave 明确提供 `max_candidates`，当候选空间超过上限时返回 `CandidateLimitExceeded`，避免在 CI 或本地任务中无限运行。

适合的规模：

- 中小型配置矩阵
- 有清晰维度和枚举值的兼容性测试
- 需要验证覆盖率的回归测试

暂不处理：

- 数值范围约束求解
- 自动执行测试环境
- 最优 covering array 求解
- 文件系统或网络 IO

这些边界让库保持轻量，也让未来维护方向更清楚。

## 场景规格层

场景规格层不是另一个独立算法，而是把生成器变成可落地的测试计划工具。它解决三个评审和维护时很常见的问题：

- 模型是否能从 README、issue 或 CI 变量里直接复现。
- 压缩后的矩阵是否仍包含业务方指定的冒烟样例。
- 生成出的用例为什么优先跑某些行，风险依据能否解释。

规格解析器保持纯字符串 API，不读取文件、不访问网络。这样它可以被命令行、Web 服务、CI 脚本或测试框架复用，同时不扩大核心库的副作用边界。

## 风险排序与质量门禁

风险排序不会改变覆盖完整性：它只在生成和覆盖验证之后，根据 `risk` 提示给用例打分。单值风险和交互风险可以叠加，因此 `browser=safari` 与 `os=macos,browser=safari` 同时命中时，排序结果会反映这条路径更值得优先运行。

`ScenarioGate` 的设计目标是让 CI 输出更像人工验收清单：

- 覆盖是否完整。
- 缺失交互是否超过允许阈值。
- 用例数量是否超出预算。
- 是否至少命中关键风险路径。
- 场景规格是否存在弱信号，例如没有约束或没有风险提示。

这也是 CaseWeave 与随机测试、覆盖率报告和提交自查工具拉开差异的地方：它产出的是一份可解释、可追踪、可门禁的组合测试计划。

## 与审查类工具的区别

CaseWeave 不读取外部仓库、不调用 Mooncakes 或 GitHub API、不检查 README、许可证、发布资格或报名材料。文档和代码里的 `audit` 只表示测试矩阵覆盖验证：输入是一组 `TestCase`，输出是哪些参数交互已经覆盖、哪些还缺失。

## 覆盖缺口修复

`plan_repair` 面向已有测试套件，而不是全新生成矩阵。它的输入是一组现有 `TestCase`，输出是一份追加计划：

1. 用 `audit` 同源的方式枚举可行候选和目标交互。
2. 把已有用例编码成内部行，并标记已经覆盖的交互。
3. 在剩余候选里选择能覆盖最多缺失交互的行。
4. 如果是 `ScenarioSpec::plan_repair`，收益相同时优先选择风险分数更高的行。
5. 每次追加后重新计算剩余缺口，直到覆盖完整或达到 `max_suggestions`。

这个算法故意保持确定性：相同的已有套件、模型、约束和风险提示会得到相同的补测建议。它不是最优 set-cover 求解器，而是一个可解释、可在 CI 中快速运行的贪心修复器。

修复计划的价值在于真实项目迁移：团队通常已经有一批历史测试，而不是从空白开始。CaseWeave 可以先验证这些历史测试，再只建议需要补的缺口，避免把已有测试全部推倒重来。

`RepairGate` 则把修复计划变成发布门禁：

- 是否已经补齐所有缺失交互。
- 建议追加的用例数量是否超出测试预算。
- 如果只允许 best-effort，剩余缺口是否在可接受范围内。
- 最大单步收益是否过低，避免生成很多低价值补测建议。
